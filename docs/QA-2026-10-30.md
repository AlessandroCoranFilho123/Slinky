# QA profundo — confiabilidade, estresse e integridade de dados

Ciclo de QA executado em 30/10/2026 sobre a v1.0.4.0 (build local da master,
instalado via MSIX assinado). Método: automação real de UI (UIA + `SendInput`/
`SendKeys`), medições WMI/`Get-Process`, verificação de bytes em disco e um app
de controle. Este documento é o registro permanente do ciclo; distingue
explicitamente PASS, FAIL, inconclusivo e não executado.

## 2. Bateria de codificações e line endings (NOVO — 9/9 PASS)

Arquivos reais gerados por byte, abertos via diálogo no app, conteúdo conferido na
UI, editados (`999` no fim), salvos e verificados **byte a byte** no disco:

| Caso | Display | Round-trip de bytes |
|---|---|---|
| UTF-8 sem BOM, LF | OK | OK (LF preservado) |
| UTF-8 com BOM, CRLF | OK | OK (BOM único + CRLF preservados) |
| UTF-16 LE com BOM | OK | OK (encoding + BOM preservados) |
| UTF-16 BE com BOM | OK | OK |
| ANSI Windows-1252 (acentos) | OK | OK (1252 preservado — round-trip oficial) |
| Emoji/Unicode (CJK, RTL) | OK | OK (UTF-8+BOM) |
| Line endings mistos | OK | OK (normalizado para CRLF no salvar — comportamento documentado do codec) |
| Arquivo vazio | OK | OK |
| Só quebras de linha | OK | OK |

Observação de método: 3 divergências intermediárias eram bugs das expectativas do
próprio script (BOM duplo em `Encoding.GetString`; `{END}` é fim de linha, não de
documento) — confirmadas por hexdump como corretas no aplicativo.

## 3. Arquivos grandes (NOVO — limites medidos)

| Tamanho | Abertura | Save | Memória do processo (PWS) | Observações |
|---|---:|---:|---|---|
| 10 MB | 15,8–17,6 s | 3,6–9,4 s | 218→295 MB | utilizável; edição e busca responsivas |
| 50 MB | 40–42 s (UI congela durante a abertura) | **2–3 min antes da correção → 13,9 s depois** | 1,0→2,6 GB | pesado, mas funcional |
| 100 MB | 84–132 s | ~2,5 min (completou após o timeout do teste; arquivo íntegro no disco) | 3,3–5,3 GB | limite prático |

Causa raiz da amplificação de memória (100 MB → ~5 GB privados): múltiplas cópias
integrais do texto — bytes brutos, string decodificada (UTF-16 = 2×), cópia
normalizada, buffer do `TextBox`, cópias do `ValuePattern`, encode no salvar e o
snapshot JSON do autosave. É um custo arquitetural do modelo "texto inteiro em
memória + TextBox"; corrigir exigiria editor virtualizado por blocos — fora do
escopo de um editor classe-Bloco de Notas. **Limites documentados em vez de
reescrita.**

**Correção implementada (freeze de save):** o autosave serializava o snapshot JSON
na UI thread (`DispatcherTimer` → `JsonSerializer` de 50–100 MB) — congelava a UI
por minutos e competia com o save manual. A serialização (e a desserialização do
startup em `FindLeftoverSnapshotsAsync`) agora roda via `Task.Run` fora da UI
thread. Efeito medido: save de 50 MB de 2–3 min → **13,9 s**.

## 5. Integridade de dados

- **Save in-place não atômico (CONFIRMADO → CORRIGIDO)**: `FileIO.WriteBytesAsync`
  sobrescreve o arquivo diretamente; um encerramento no meio da gravação poderia
  deixar um arquivo truncado. Correção: `Note.WriteBytesSafeAsync` grava em um
  `.tmp` com nome GUID na mesma pasta e troca via `MoveAndReplaceAsync`
  (renomear no mesmo volume é a operação segura); qualquer falha na rede de
  segurança cai de volta na escrita direta — salvar nunca falha por causa da
  proteção. Verificado: round-trip de bytes idêntico em todos os casos da bateria
  e **nenhum `.tmp` residual**.
- Snapshot do recovery já era atômico (tmp + `MoveAsync`) — confirmado no código.
- Ciclos save/open repetidos preservam encoding/BOM/line-endings (bateria acima).
- Conteúdo restaurado do recovery não perdeu texto em nenhum teste (incluindo o
  cenário de duas janelas de 29/10).
- **Não executado**: interrupção real de processo no meio de um save (janela de
  milissegundos, não reproduzível com confiabilidade via automação); mitigação
  implementada elimina o estrago mesmo nesse cenário.

## 6. Segurança e dependências

- Superfície varrida: sem rede (`HttpClient`/sockets ausentes); `Process.Start`
  apenas com `Environment.ProcessPath` (próprio exe, "Nova janela"); paths de
  usuário vêm exclusivamente de pickers/FAL; `Path.Combine` só com
  `LocalFolder`/`BaseDirectory` (próprios do pacote).
- Serialização: `System.Text.Json` para POCOs próprios, lidos da pasta
  `LocalState` do próprio pacote — sem desserialização polimórfica.
- Dependências: Windows App SDK 1.8 granular (WinUI 1.8.250906003, Runtime
  1.8.250916003, DWrite 1.8.25090401 — linha MS suportada); WebView2 1.0.3179.45
  (transitivo do WinUI, não usado pelo app); xUnit 2.9.3/SDK 17.11.1 (só teste).
  Nenhum aviso de vulnerabilidade conhecida verificado para essas versões.
- Temporários: recovery e save usam nomes GUID e limpam em `finally`. Resíduo
  teórico: um `.slinky-tmp` pode permanecer se o processo morrer no meio da
  gravação (arquivo pequeno, sem impacto funcional) — melhoria futura possível.
